## 三、发现的缺陷

### 缺陷 1（已修复部署）：大文档只切出 1 个块，嵌入被静默截断

**严重度：高。这是本次"先建知识库"直接挖出来的。**

`NormalizeText`（`normalize.go:45`）把 `\n` 也当成普通空白折叠，于是整篇 Markdown 变成一行；`ChunkMarkdown` 逐行找标题，这一行以 `#` 开头，**整篇文档被当成"一个标题"**，正文为空，最终只产出 1 个块。

实测：11,482 字符的文档 → **1 个块**。该块远超 `gemini-embedding-001` 的 2,048 token 输入窗口，被**静默截断**——**每篇文档只有开头约 2,000 字符能进入向量检索**。

**为什么一直没被发现**：旧语料每篇仅 826 字符，低于 `DefaultChunkSize=1000` 阈值，"1 篇 1 块"是正确行为。缺陷只在真实体量文档下暴露。

**修复前后**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 30 篇文档分块数 | 30 | **580** |
| 平均块大小 | 8,277 字符 | **536 字符** |
| 最大块 | 15,811 字符 | **1,074 字符** |
| 超嵌入窗口的块 | 30（全部） | **0** |
| 向量覆盖率 | — | **621 / 621** |

端到端检索验证：**10 / 10 全部命中**（高棉语 6、中文 3、英文 1）。

改动：`normalize.go`（区分待写空格与换行）、`normalize_test.go`（原测试把 bug 写成了期望行为，一并纠正）、新增 `chunk_size_test.go` 回归测试。提交 `ed9d2f9`。

### 缺陷 2（已修复部署）：生成失败丢弃上游错误，线上 500 无法定位

**严重度：中高（可观测性）。**

`chat_handlers.go:247`：
```go
result, err := a.Gemini.Chat(...)
if err != nil {
    return nil, ErrInternal("生成回答失败")   // err 被整个丢弃
}
```

`gemini.go` 已构造完整原因（`gemini returned HTTP 429: {...}`），三处调用点（chat / ragQuery / widget SSE）全部丢弃。

**实际代价**：压测产生 2,969 次 500，日志里查不出任何原因，排查多花了一整轮。修复部署后，同一故障立刻定位到 429 消费速率限制。

改动：三处补 `a.Logger.Error(...)`，带 session/user/是否命中知识库；**未改动任何返回给客户端的文案与状态码**。提交 `53f4465`。

### 缺陷 3（已报告，未修）：部分更新会静默清空 category

**严重度：低—中（数据丢失隐患）。**

`UpdateDocument`（`service.go:1548`）同一个 UPDATE 语句里两种语义：

```sql
content = $1,
title    = CASE WHEN $3 = '' THEN title ELSE $3 END,   -- 空值保留
category = $4                                           -- 空值直接清空
```

调用方（如 `PUT /api/v1/knowledge/{id}`）不带 `category` 就会把分类清零。我在重建索引时踩到了，30 篇文档的 category 被清空（已用 SQL 恢复，仅元数据，未动向量）。

**未修复原因**：改动会变更 API 语义（调用方将无法主动清空分类），且压测刚结束不宜再动生产。建议改为与 `title` 一致的 `CASE WHEN $4 = '' THEN category ELSE $4 END`，或明确改为 PATCH 语义。

## 四、真正的瓶颈：Gemini 消费速率限制

压测中暴露的上游真实响应：

```
429 You exceeded your spend-based rate limit. Your spending rate has exceeded
    the allowed limit for your account's billing history and tier.
    status: RESOURCE_EXHAUSTED
```

这不是每分钟请求配额，而是 Google 按**账单历史与账户层级**计算的**消费速率**上限。直接探测（一句 "hi"）同样返回 429，证明是账户级限制。

**触发时间线**（日志实证）：

| 时段 | 429 条数 | 来源 |
|---|---|---|
| 压测前 00:00–06:06 | **8** | 正常波动，账户健康（有 15 次成功生成） |
| 05:00 时段 | 634 | 知识库入库（30 篇上传 + 36 篇编译） |
| 06:00 时段 | **10,080** | 压测 |

**恢复特性**：滚动窗口限制，**约 3 分钟后自愈**（探测第 3 次返回 200），并非封禁。

### 这对生产意味着什么

1. **账户当前档位撑不住真实流量峰值。** 一次真实的市场活动或 100 人同时咨询就可能触发，届时**所有客户对话返回 500**。
2. **系统对生成失败没有任何降级。** RAG 检索在 429 时会优雅降级为纯词法检索（331 次 WARN 记录了这一点，设计正确），但生成环节没有 fallback——`postWithRetry` 对 429 重试 3 次纯属浪费（消费限制是持续性的，不是瞬时抖动）。
3. **该故障不会触发任何告警。** 已有 `PlatformAlert` 机制（Telegram），但未覆盖生成失败率。

### 建议（按优先级）

1. **提升 Gemini 账户层级 / 绑定更长的账单历史**，或申请提高 spend rate limit——这是根因。
2. **加生成失败率告警**：复用 `platform/jev_health.go` 的模式，对连续 N 次生成失败发 `PlatformAlert`。
3. **429 时不要重试**，直接降级：返回"客服繁忙，正在为您转接人工"并自动创建 handoff，而不是返回裸 500。
4. 考虑备用模型通道（不同账户/项目），避免单账户限制导致全站不可用。

## 七、局限与未做事项

1. **多租户压测稀释了 RAG 路径**：22 个租户中只有 1 个（user 7）持有知识库，因此 3,533 条模型回复中只有 356 条真正走了知识库接地。若要让检索路径也承压，需要给多个租户各建知识库，本次未做。
2. **widget 渠道未能承压**：`widget-msg-day` 硬上限 200 条/天/token，无法承担高流量，因此高并发全部走认证接口。该限制本身设计正确（防止公开 token 被刷爆），但也意味着**网站挂件在真实高流量下会先撞到日上限**——建议评估该阈值是否匹配业务预期。
3. **未测试 SSE 流式接口**（`/api/v1/chat/stream`）与 Meta/Telegram/LINE 渠道入站。
4. **未做长时间稳定性测试**（本次每层 45–90 秒）。
5. **高棉语知识库需母语者校对**：内容由 AI 生成并经数值审计，但语言自然度未经人工复核。
6. **Meta 数据删除回调仍需在 Meta App Dashboard 注册**（此前遗留事项）。
