# RelayChat 订阅收费方案

面向柬埔寨中小商家的 AI 客服订阅设计。本文档基于**当前代码的实际能力**与**生产库的实测数据**，不是通用 SaaS 模板。

> ⚠️ **先说数据可信度**：生产环境目前只有 4 个测试账号、全平台 119 次模型调用、
> 累计成本 **$0.0898**（自 2026-08-28）。样本量不足以反推真实单位经济性。
> 下文成本模型是**从模型定价与实测 token 结构推算**的，假设已逐条标注，
> 上线后必须用真实数据校准（见 §6）。

---

## 一、现状：计费骨架已有什么

| 组件 | 状态 |
|---|---|
| `tenant_billing` 表 | 有：`plan` / `monthly_message_quota` / `monthly_doc_quota` / `messages_used` / `docs_used` / 30 天账期 |
| 套餐切换 | `PUT /billing/plan`，**仅 platform_admin**，额度硬编码在 `setPlan`（free 500/20、pro 5000/500、enterprise 无限） |
| 文档配额 | **已强制**（`consumeDocQuota`，3 个上传入口，超限返回 402） |
| 消息配额 | **只计数，不强制**（`bumpMessagesUsed` 注释原文：enforcement is a deliberate product decision, kept off） |
| 支付集成 | **完全没有**。零代码 |
| 前端 | 管理后台 Growth 页有 `BillingCard`，可看用量、平台管理员可切套餐 |

**结论：骨架够用，但离"能收钱"还差三件事** —— 计量口径有洞、配额不强制、没有收款通道。

## 二、成本模型

### 2.1 实测 token 结构

生产库 `token_usage` 聚合（119 次调用）：

| 指标 | 值 |
|---|---|
| 平均输入 | 1,882 tokens |
| 平均输出 | 92 tokens |
| 单次调用成本 | ≈ **$0.0008** |

输入远大于输出 —— 这是 RAG 的结构性特征：知识库片段（每片截断 800 字符，表格片段 2000 字符）被塞进 prompt。

### 2.2 一次「AI 应答」的真实成本

一个客户消息触发的**不是一次**模型调用，而是一串：

| 环节 | 估算 token | 说明 |
|---|---|---|
| 查询改写 | ~500 in / 30 out | 有历史时才跑 |
| 检索重排 | ~2,500 in / 100 out | 15 个候选片段 |
| 轮次分类 | ~800 in / 20 out | 仅部分路径 |
| 主应答 | ~1,900 in / 92 out | 实测均值 |
| **合计** | **≈ 5,700 in / 240 out** | |

**≈ $0.0023 / 次 AI 应答**（按代码内定价常量 $0.30 / $2.50 每 1M）

一次典型客户对话（约 8 轮）≈ **$0.02**。
一个每月 1,000 轮的商家 ≈ **$2–3/月的模型成本**。

### 2.3 关键结论：模型成本**不是**定价约束

在 $29/月 的档位上，商家需要跑 **约 12,000 次应答**才能让模型成本吃掉全部收入。

**所以配额的作用是防滥用与公平使用，不是成本回收。** 真正的成本在别处：

- **支持人力** —— 最大的隐性成本。这也是本项目的一个真实优势：平台 bot 已经有支持收件箱 + 双向中继，边际支持成本远低于普通 SaaS
- 服务器 / Postgres / Redis（当前与 WMS 同机，未来要独立）
- **R2 存储** —— 入站媒体、TTS 音频、头像都在存，**当前完全没有计量**，且随客户量线性增长
- 渠道侧的平台费用（WhatsApp 对话计费由商家自己承担，注意不要重复计费）

## 三、套餐设计

计价单位用 **「AI 应答条数」** —— 商家能理解，映射价值直接，且已在计数。

| | ឥតគិតថ្លៃ Free | Starter | **Pro** | Enterprise |
|---|---|---|---|---|
| **月费** | $0 | **$9** | **$29** | 面议（≥$99） |
| AI 应答 / 月 | 300 | 1,500 | 10,000 | 公平使用 |
| 知识库文档 | 20 | 200 | 1,000 | 不限 |
| 消息渠道 | 1 | 3 | 全部 7 | 全部 |
| 坐席账号 | 1 | 3 | 10 | 不限 |
| 网站挂件 | — | ✓ | ✓ | ✓ |
| 知识编译 / 矛盾评审 | — | — | ✓ | ✓ |
| SLA / 路由 / 宏 / Webhook | — | — | ✓ | ✓ |
| 营销群发 | — | — | 3,000 / 月 | 不限 |
| CSV 导出 | — | ✓ | ✓ | ✓ |
| 支持 | 文档自助 | Telegram 48h | Telegram 8h | 专属 |

**设计要点**

- **Pro 是锚点**。功能和额度都刻意让 Pro 显得划算，Starter 是"先跑起来"，Free 是价值验证
- **Free 的 300 条够证明价值，不够当生产用** —— 一个月能跑出真实数据，但撑不住一个正常商家
- **Starter $9 是为柬埔寨微型商家设的**。传统 SaaS 会担心 $9 客户的工单成本吃掉收入，但本项目的支持走平台 bot，边际成本低 —— 这是把 Starter 定在 $9 而不是 $19 的依据
- **Enterprise 不是"更大额度"**，而是：多租户隔离加固、数据驻留、SLA 承诺、专属支持。额度写"公平使用"而非"无限"，保留滥用时的干预权

## 四、计量口径（最容易出错的地方）

**建议口径：「AI 成功发出的应答条数」。**

不是收到的客户消息数 —— 客户连发三条只回一条，按消息计费对商家不公平，也会逼商家去限制客户发言。

现状实现的三个洞，**上线前必须补**：

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| 1 | 配额**只计数不强制** | `platform/telegram_notify.go:183` | 超额仍继续服务，收不到钱 |
| 2 | **网站挂件完全不计数** | `widget_handlers.go`（无 `bumpMessagesUsed` 调用） | 挂件是流量最高的终端界面，全部免费 |
| 3 | 计费行**懒创建** | `getBilling` 无行时返回假 free | 用量看板与实际不符 |

补 #2 时注意：挂件已有自己的防滥用上限（20 条/分/IP、200 条/天/token、20 会话/小时/token）。**这些是防刷，不是计费**，两者要并存而不是互相替代。

## 五、收款：分阶段，从零代码开始

### 阶段 0 —— 立刻可用（当前架构已支持）

**运营者人工收款。** 平台 bot 已经有商家支持收件箱和双向中继，商家本来就在 Telegram 里：

1. 商家在后台点「升级」→ 生成一条请求，落到平台 bot 的支持收件箱
2. 运营者回复 **KHQR 收款码**（柬埔寨国家二维码标准，几乎所有银行 App 都能扫）
3. 到账后运营者在平台上改套餐

**需要的代码**：一个 `/setplan <租户> <套餐>` 运营者命令。其余全是现成的。

这是**唯一现在就该做的部分** —— 在验证有人愿意付钱之前，不要建支付系统。

### 阶段 1 —— 自助升级

- 后台「升级」按钮 → 展示套餐对比 → 生成 KHQR 订单
- 对账靠**轮询银行流水**或人工确认
- 需要新表：`billing_orders`（订单号 / 租户 / 套餐 / 金额 / 状态 / 支付凭证 / 到期时间）

### 阶段 2 —— 自动化

- **ABA PayWay** 或 **Bakong/KHQR API** 的订阅接口
- 自动续费、失败重试、宽限期、发票
- 这时才值得建 `billing_payments` 流水表

**支付方式优先级**：KHQR / Bakong > ABA PayWay > Wing。柬埔寨商家不用信用卡，**不要按欧美习惯设计 Stripe 优先的方案**。

## 六、上线后必须校准的假设

样本量太小，以下都是待验证的推断：

| 假设 | 如何验证 |
|---|---|
| 单次应答 ≈ $0.0023 | 真实流量跑一个月后，用 `token_usage` 重算；注意现在**嵌入调用根本没记账** |
| 一次对话 ≈ 8 轮 | 从 `chat_messages` 按会话统计分布 |
| 商家月均 1,000 轮 | 同上，取中位数而非均值（长尾会拉偏均值） |
| $29 是合适锚点 | 前 20 个付费商家的转化率与流失率 |

### 一个必须先修的成本统计 bug

`internal/usage/usage.go` 的定价常量**硬编码为 Gemini 2.5 Flash**（$0.30 / $2.50 / $0.03 每 1M），但生产实际服务的是 **`gemini-3.8-flash`**（`/ready` 与启动日志可证）。

**当前后台显示的所有成本数字都是按错误单价算的。** 建立在错误成本上的定价决策没有意义 —— 这个要先修，并且应该**按模型分别定价**，而不是全局常量。

另外：**嵌入调用（`gemini-embedding-001`）完全没有进 `token_usage`**，所以文档摄入成本当前不可见。文档数量是套餐卖点之一，这块成本必须能算出来。

### 功能门控的实现难度不一样

套餐表里列的功能，门控成本差别很大：

| 功能 | 现状 | 门控做法 |
|---|---|---|
| 知识库文档数 | **已强制** | 无需改动 |
| AI 应答条数 | 只计数 | 加检查即可 |
| 坐席数 | 每租户独立行 | `addTeamAgent` 里查 `COUNT(*)` |
| 渠道数 | 每租户独立行 | `upsertPlatformConfig` 里查计数 |
| 挂件令牌 | 每租户独立行 | 同上 |
| SLA / 路由 / 宏 / 营销 | 每租户独立行 | 加检查即可 |
| **知识编译 / 矛盾评审** | ⚠️ **全局开关** | **需要改成按租户** |

最后一行要注意：编译开关是 `rag:compile_enabled` 这个**全局 Redis 键**（`/admin/rag/settings`，仅平台管理员可改），不是按租户的。

**要让"知识编译"成为 Pro 专属功能，得先把它从全局开关改成按租户判定** —— 这是本方案里唯一一处非机械性的改动。

### 审计缺口

`setPlan` 是 platform_admin 专属、且直接改变计费额度的操作，**但它不被审计**。

审计中间件（`router.go`）的判定是 `path 含 "/admin/" 或 "/platform/"`，而路由是 `PUT /api/v1/billing/plan` —— **两个都不匹配**。

同样的缺口影响其它挂在 `/billing/` 下的路由。建议改为**显式的路由级审计标记**，而不是靠路径字符串猜。

### 超额策略（产品决策，非技术）

建议**软限**而非硬限：

- 达到 100% → 正常服务，推送提醒（平台 bot 已有通知通道）
- 达到 120% → AI 降级为"转人工"，不再产生新成本
- 不直接 402 掐断 —— 商家在客户面前被掐断，失去的信任远超那点超额成本

Free 档可以硬限（300 条本来就够验证价值），付费档一律软限。

---

## 八、不建议做的事

- **不要按 token 计费** —— 商家无法理解，也无法预测账单
- **不要做"无限"套餐** —— 除非额度真的无限，否则写"公平使用"并保留干预权
- **不要在建支付系统之前做定价页** —— 阶段 0 的人工收款能验证付费意愿，成本几乎为零
- **不要按欧美习惯先接 Stripe** —— 柬埔寨商家的支付习惯是扫码转账
